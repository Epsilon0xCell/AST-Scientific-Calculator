AST-Scientific-Calculator

A command-line calculator in one Python file, calculator.py. I parse each expression into a tree and walk only the nodes I allowed on purpose. Nothing is ever handed to eval.

An expression is not a flat line to me. It is a tree, and the shape of the tree is the order the work happens in. This drawing follows whatever is in the display, key by key. Multiplication sits deeper than addition because it binds tighter, and that is why 2 + 3 * 4 is 14 and not 20.

Bench note 01How it parses

When I run python3 calculator.py "sqrt(144) + 2 * pi", the text goes to the ast module first, not to an evaluator. Parsing turns it into a tree of nodes: a call at the top, numbers and names at the leaves. My evaluate function then walks that tree and answers one question at each node: did I allow this exact thing?

Three tables do the allowing. FUNCTIONS names 18 functions, CONSTANTS names pi, e, and tau, and OPERATORS names seven operators. The name ans is handled on its own, because it changes after every result. Here are the two tables that carry most of the rules, copied from calculator.py at lines 28 to 34 and lines 41 to 46:

FUNCTIONS = {
    "sqrt": math.sqrt, "sin": math.sin, "cos": math.cos, "tan": math.tan,
    "asin": math.asin, "acos": math.acos, "atan": math.atan,
    "log": math.log, "log2": math.log2, "log10": math.log10, "ln": math.log,
    "exp": math.exp, "abs": abs, "floor": math.floor, "ceil": math.ceil,
    "round": round, "min": min, "max": max,
}
OPERATORS = {
    ast.Add: lambda a, b: a + b, ast.Sub: lambda a, b: a - b,
    ast.Mult: lambda a, b: a * b, ast.Div: lambda a, b: a / b,
    ast.FloorDiv: lambda a, b: a // b, ast.Mod: lambda a, b: a % b,
    ast.Pow: lambda a, b: a ** b,
}

It runs two ways. With an argument it prints one result and exits, and the README example above prints 18.2831853072, which I checked by running it. With no argument it opens a REPL with a calc> prompt, where help lists the functions and constants, history shows the expressions that worked, and quit, exit, or q leaves. A line that fails leaves ans and history alone.

Bench note 02What it refuses

The refusal is the feature I care about most. eval would run whatever it is handed. My evaluator names a short list of things it will do, and every other node type falls through to one error at the bottom of evaluate. These are lines 89 to 105 of calculator.py, the call check and the fall-through:

    if isinstance(node, ast.Call) and isinstance(node.func, ast.Name):
        name = node.func.id
        if name not in FUNCTIONS:
            raise CalculatorError(f"unknown function: {name}")
        # I reject keyword arguments outright. None of the functions I
        # allow need them, and accepting them would widen the surface
        # for no gain in a calculator.
        if node.keywords:
            raise CalculatorError("keyword arguments are not supported")
        # I evaluate the arguments in order and pass them as plain
        # positional values. A starred argument has no handler in this
        # function, so it falls to the error at the bottom.
        return FUNCTIONS[name](*[evaluate(a, ans) for a in node.args])
    # Anything I did not name above lands here: attribute access,
    # subscripts, comparisons, and every other node type. I refuse it
    # by name so the user can see what part I rejected.
    raise CalculatorError(f"unsupported syntax: {type(node).__name__}")

Strings are refused as constants, keyword arguments are refused outright, and bitwise operators never reach an implementation because they are not in OPERATORS. The panel above keeps the same habit: type foo(2) into it and it answers the same way.

Three of those deserve a sentence each. The 0.1 + 0.2 line prints 0.3 because format_result caps output at 12 significant digits, which hides the long binary tail. The minus 2 squared line is minus 4 because the power binds before the unary minus, the same shape the tree above draws. And round(2.5) is 2 because Python rounds a half to the nearest even number; the panel copies that too, instead of rounding every half up.

Math failures fold into the same error type: 1 / 0 answers division by zero, and sqrt(-1) answers math domain error. Whole floats print as whole numbers, so sqrt(16) prints 4, not 4.0.

Bench note 04Honest notes

The evaluator is recursive because the tree is recursive, and that has a real cost. An expression chained thousands of terms deep used to die with a RecursionError traceback. calculate now catches that and answers with a plain line instead. Lines 120 to 126 of calculator.py:

    try:
        return evaluate(tree, ans)
    except RecursionError as exc:
        # A chain with thousands of terms can parse fine and still walk
        # thousands of frames deep in my evaluator. I refuse it as too
        # deep instead of letting the interpreter kill the process.
        raise CalculatorError("expression is nested too deeply") from exc

My security audit of this repo came back clean: a closed whitelist evaluator with no eval anywhere in it. One note from that audit is worth keeping on the bench. The Pow node applies Python exponentiation directly, so a huge exponent typed by the person at the keyboard costs local time and local memory only. There is no server here to hurt, and the person typing pays for their own exponent. The panel is blunter: it works in browser numbers and reports a result that overflows them as an error.

Two smaller honesty items. min and max in the real program are the Python builtins, so they want at least two values to compare in normal use. And there are no test files in this repo yet, so the checks on this page are runs I did by hand and wrote down, not a suite that reruns itself.
